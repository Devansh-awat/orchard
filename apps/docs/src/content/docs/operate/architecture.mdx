## The pieces

| Component                  | What it is                                   |
| -------------------------- | -------------------------------------------- |
| **Frontend**               | SvelteKit web app                            |
| **Server**                 | NestJS API and Prisma, the control plane     |
| **Gateway**                | Go edge proxy                                |
| **Builders**               | BuildKit jobs that build tenant images       |
| **Control-plane Postgres** | Orchard's own database, run by CloudNativePG |
| **Redis**                  | Event bus and caching                        |
| **Registry**               | Where built images are pushed and pulled     |

Tenant apps and databases run in their own namespaces, separate from the control
plane.

## The mirror

The API does not ask Kubernetes every time you load a page. Informers watch
cluster objects and **mirror their state into Postgres**, and reads are served
from there with live escape hatches for the cases that need the truth right now.

This is why the dashboard stays responsive with hundreds of apps, and why it
keeps working while the API server restarts. When the mirror and the cluster
disagree, the cluster wins: the mirror is a cache of reality, never the source of
it.

Changes made outside Orchard, with `kubectl` directly, are adopted into Orchard's
state rather than being fought or silently overwritten.

## Writes

Cluster writes go through a **retrying apply queue** instead of happening inline
in the HTTP request. A deploy request records intent and returns; the queue
reconciles it against the cluster, retrying on conflict. A transient API server
error becomes a retry rather than a failed deploy the user has to repeat.

## Events

State changes flow over Redis Streams to the frontend as server-sent events, so
build steps advance and pods change colour without polling. Reconnecting replays
from the last event seen rather than starting blind.

## Leader election

Components that must not run twice, informers, schedulers, the protection proxy's
guard, use lease-based leader election, so the API can run multiple replicas
without duplicating work.

## Queues and API pods

Queue workers run as a separate deployment from the API pods, so a long queue of
builds does not compete with serving the dashboard.
