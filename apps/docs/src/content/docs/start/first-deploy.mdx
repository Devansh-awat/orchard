## 1. Connect GitHub

Orchard talks to GitHub through a GitHub App. On a fresh instance, an admin
creates it through the **manifest flow**: Orchard generates the app manifest,
GitHub creates the app, and the credentials come back automatically. There is no
step where you copy six values between two tabs.

Once the app exists, each person links their own GitHub account, and Orchard
only ever sees the repositories that account granted.

## 2. Create an app

**New → GitHub Repository.** Pick the repo and a branch.

Orchard then reads the repository and fills in what it can:

- the **Dockerfile** and its build stages, so a multi-stage build targets the
  right final stage
- the **port** the container exposes
- **environment variables** declared in the image, like `NODE_ENV` or `PORT`

Check the build stage in particular. A multi-stage Dockerfile whose last stage is
`runner` should build `runner`, not `base`; picking the wrong one produces an
image with no application in it.

## 3. Deploy

Press **Deploy**. You land on a progress page with five steps:

1. Scheduling builder
2. Building image
3. Pushing image
4. Creating app
5. Done

Build logs stream as they happen, so a failure shows you the line that broke
rather than a red cross. If it fails, the app stays in a failed state and you can
fix the Dockerfile and redeploy without recreating anything.

When it finishes you get an HTTPS URL on the instance's app domain, and every
push to that branch deploys itself from then on.

## 4. Give it a database

**New → Database** creates a managed PostgreSQL instance in the same project.
When it is ready, the connection page shows the URI, host, port, database, user
and password, with copy buttons and four formats (`URI`, `psql`, `.env`, `JDBC`).

Add the connection string to the app's variables and redeploy. Details in
[Databases](/data/databases/).

## 5. Watch it run

The app's **Overview** tab has live logs on the left and CPU, memory and replicas
on the right. The replica slider scales it. The **Shell** button opens a terminal
inside the running container.

## If the build fails

The most common causes, in order:

- **Wrong build stage.** See above.
- **The app needs a database at build time.** Migrations in the entrypoint run at
  _start_, not build, so this usually shows up as a crash loop instead.
- **The repo does not build with the toolchain in its own Dockerfile.** Orchard
  runs exactly what the Dockerfile says. If it fails in Orchard, it usually fails
  locally too.

A crash loop after a successful build shows up as **Failed** with the container's
own logs attached, including the logs of the container that already died.
